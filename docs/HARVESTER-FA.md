# ضبط تیک — قرارداد فایل و تنظیمات

## چیدمان خروجی

```
MQL5/Files/harvester/
├── symbols.json                  # فهرست نمادهای انتخاب‌شده + ساعت هفتگی
├── status.json                   # ضربان: تعداد تیک، خطا، سن هر نماد
└── ticks/
    ├── BTCUSD/
    │   ├── 20261126.csv
    │   └── 20261127.csv
    ├── EURUSD/
    │   └── 20261126.csv
    └── ...
```

## قالب CSV

```
time_msc;time;bid;ask;last;volume;flags
1764151200123;2026.11.26 08:40:00;91234.12;91240.50;91238.00;0.12;6
```

| ستون | معنی |
|---|---|
| `time_msc` | میلی‌ثانیه‌ی یونیکس (منبع اصلی ترتیب و تجمیع) |
| `time` | زمان سرور به وقت ترمینال (`YYYY.MM.DD HH:MM:SS`) — فقط برای خوانایی |
| `bid` / `ask` | قیمت‌های لحظه‌ای |
| `last` | آخرین معامله (در فارکس/CFD معمولاً ۰) |
| `volume` | حجم تیک (`volume_real`) |
| `flags` | بیت‌های `TICK_FLAG_*` متاتریدر |

پایتون نسخه‌ی mid و اسپرد را از `bid/ask` می‌سازد، پس اگر بروکر `last` نداد هم
مشکلی نیست.

## چرا فایل و نه سوکت؟

* هیچ `WebRequest`، هیچ whitelist، هیچ پورت باز، هیچ مجوز شبکه‌ای لازم نیست.
* کرش/ری‌استارت پایتون هیچ تأثیری روی ضبط ندارد. ترمینال مستقل کار می‌کند.
* خواندن **افزایشی** است: پایتون برای هر فایل یک `offset` در
  `var/ingest_state.json` نگه می‌دارد و هر بار فقط بایت‌های تازه را می‌خواند.
* خط نیمه‌نوشته‌ی انتهای فایل نادیده گرفته می‌شود و بار بعد خوانده می‌شود
  (بدون خطای پارس).

هزینه: روی SSD معمولی، ۱۰–۲۰ نماد با ۲۵۰ms نظرسنجی معمولاً < ۲٪ CPU و
چند ده مگابایت در روز است. حجم دقیق به تعداد تیک بروکر بستگی دارد؛
`status.json → total_ticks` و اندازه‌ی پوشه را روز اول بسنج.

## ورودی‌های اکسپرت

| ورودی | پیش‌فرض | کار |
|---|---|---|
| `InpOutDir` | `harvester` | پوشه‌ی خروجی داخل `MQL5/Files` |
| `InpPollMs` | `250` | فاصله‌ی خواندن `CopyTicks` برای هر نماد |
| `InpFlushEveryTicks` | `200` | هر چند تیک فایل flush شود |
| `InpStatusEverySec` | `5` | فاصله‌ی نوشتن `status.json` |
| `InpBackfillSec` | `900` | در شروع چند ثانیه عقب‌تر برود |
| `InpMaxFileMB` | `512` | سقف فایل روزانه؛ بعد از آن ضبط آن نماد متوقف می‌شود |
| `InpSymbolsCsv` | خالی | فهرست دستی با کاما؛ خالی = خودکار |
| `InpAutoDiscover` | `true` | کشف خودکار نمادهای ۲۴ ساعته |
| `InpMinWeeklyHours` | `100` | آستانه‌ی «۲۴ ساعته» بودن |
| `InpMaxSymbols` | `40` | سقف تعداد نماد |
| `InpForceMarketWatch` | `true` | افزودن خودکار نماد به Market Watch |
| `InpMaxTicksPerPoll` | `20000` | سقف تیک هر نظرسنجی هر نماد |
| `InpStopOnFileLimit` | `true` | توقف ضبط نماد در صورت پر شدن فایل |
| `InpVerbose` | `true` | لاگ در تب Experts |

## رفتار در شرایط مرزی

* **چرخش روز**: نیمه‌شب سرور، فایل روز جدید باز می‌شود؛ فایل قبلی flush و بسته
  می‌شود. پایتون هر دو فایل را می‌خواند، پس مرز روز داده گم نمی‌شود.
* **تکرار تیک**: تیک‌هایی که `time_msc` آن‌ها ≤ آخرین تیک نوشته‌شده باشد دور
  ریخته می‌شوند؛ بازخوانی یک بازه هرگز رکورد تکراری نمی‌سازد.
* **بک‌لاگ**: اگر ترمینال چند دقیقه قطع شده باشد، `CopyTicks` بازه‌ی موجود در
  حافظه را می‌دهد (معمولاً چند ساعت اخیر) — پس همیشه `last_msc+1` درخواست می‌شود.
* **Market Watch خالی**: `SymbolSelect` برای هر نماد صدا زده می‌شود؛ اگر نماد در
  بروکر نباشد، در لاگ خطا و در `status.json` شمارش خطا ثبت می‌شود.
* **فرمت نام فایل**: تاریخ **UTC** نیست، تاریخ **سرور** است (`TimeTradeServer`).
  برای تحلیل روزانه همین کافی است؛ اگر بروکرت offset غیرمعمول دارد، در گزارش
  ستون `time` را ملاک بگیر.

## پاک‌سازی و آرشیو

داده‌ی خام تیک ارزش پژوهشی دارد؛ قبل از حذف، فشرده کن:

```bash
cd "<MQL5/Files>/harvester/ticks"
tar -cJf ~/archive-2026-11.tar.xz 202611*
# بعد از اطمینان از سالم بودن آرشیو، فایل‌های ماه قبل را حذف کن
```

پایتون فقط از فایل‌های موجود می‌خواند؛ حذف فایل قدیمی چیزی را نمی‌شکند چون
`processed:<symbol>` در SQLite جلوتر از آن است.
